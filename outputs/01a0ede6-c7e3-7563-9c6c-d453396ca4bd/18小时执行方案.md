# 造物营：18 小时项目检查执行方案

版本：2026-09-30，准备材料 v0.1。对象：个人项目评审。此方案以现有产品代码和你的设计工作经历为依据；评测用例已设计，新的真实模型评测尚未执行。

你现在最需要完成的，是一条老师能核查的链路：**一个真实设计需求 → 一次有记录的生成 → 可复核的评分 → 一个有证据的 Badcase → 一次同条件回归。** 先把这条链做完整。无需在 18 小时内补完通用 AI 平台、大数据看板或自动审美评审器。

## 1. 把项目讲清楚

**产品定位：** 面向电商设计师和商家运营的 PC 图片创作工作台。用户放入商品图，可选择背景、文案和排版约束，系统批量给出多个视觉样稿，用户挑选、修改并导出。

**当前最重要的用户价值：** 缩短从商品素材到“值得继续采用的设计方向”的时间。第一步解决同一商品的多方向探索；不同 SKU 套图是后续场景。

**成功不等于生成成功。** 一张图至少要商品准确、符合需求、设计完整、文件可用，且设计者愿意采用。这里的“可采用”代表设计生产环节的人工判断，尚不代表真实广告 CTR、销售转化或已完成全部商用授权审查。

可直接对老师说：

> 我是电商设计背景，日常工作包含风格确认、找背景、商品合成与套图。这个个人项目先聚焦“同一商品快速获得多个可采用的视觉方向”。目前我发现背景和版式同质化，所以把评价重心从“生了多少张”改为“一个任务能否得到至少一张可采用样稿”，再用逐图评分和生成链路定位问题。

## 3. 指标体系：先盯一个价值指标

**产品北极星：每周获得采用的创意任务数。**

- 按北京时间自然周统计；周内首次出现有效采用的逻辑任务去重。必须能指向保存成功的具体图片与版本。
- 一次商品 + 设计需求建立 task_id；失败重试沿用该 task_id，产生新的 job_id。新增商品或重写需求才建立新任务。
- 开发、模拟、内部评测从正式用户周指标排除。撤销采用保留历史，可另报期末仍采用任务数。
- 当前缺事件历史和稳定逻辑任务标识，所以这是确定的指标方案，不能展示虚构的周趋势。

**当前离线核心：首轮可采用任务率。** 分子是首轮至少有一张被评为可采用的真实视觉任务，分母是本批全部有效已执行视觉任务。模型失败、保存失败计入分母；待评审不是拒绝，未评审清零前不给最终比率。工程模拟不混入。

配套只先看 5 类：端到端成功率、商品事实错误、组内视觉差异、首次可用结果耗时、每个采用任务成本。工作簿还给出导出请求与评审覆盖率口径。

**不要先填“采用率 80%”或“效率提升 50%”。** 先测当前基线。商品事实正确是采用的硬门槛；质量与耗时目标待第一轮结果后再定。小样本用“3/4 个任务”表达，比只写“75%”更容易复核。

## 4. 埋点如何最小落地

用户链路：上传 → 抠图 → 受理生成 → 设计策略 → 生图 → 合成保存 → 用户看见 → 采用/拒绝 → 请求导出。

工作簿列了 12 个事件的触发位置、字段、去重和当前实现状态。18 小时内优先让一条任务可串起来，不用先引入复杂的数据平台：

1. 在已有 generation_jobs 上明确 task_id、job_id、input_revision、workflow/prompt/layout 版本。
2. 用结构化 JSON 或附属阶段表记录规划、生图、合成、保存的开始、结束、结果及错误。先用 job_id 作 trace_id；每步一个 span_id，保存 parent_span_id。
3. 用户看见结果、逐图反馈使用事件记录。反馈保存成功后才计数；事件用 event_id 去重。图片采用必须关联 asset_id 和版本。
4. 服务端负责受理、模型、保存等事实；客户端负责抠图状态和实际展示。客户端重放不能制造多次生成或采用。
5. 同时保存失败。拿“失败发生在规划、模型还是存储”解释故障。提供者返回图片 URL 并不等于成品已保存。

最小 trace 内容：

```json
{
  "task_id": "example-task",
  "job_id": "example-attempt-1",
  "is_simulated": true,
  "input_revision": 1,
  "workflow_version": "proposed-v1",
  "stages": [
    {"name":"plan","status":"succeeded","prompt_version":"plan-v1"},
    {"name":"generate","status":"succeeded","output_ref":"mock://generated"},
    {"name":"persist","status":"failed","error_code":"STORAGE_WRITE_FAILED"}
  ]
}
```

上面是字段结构示例，不是真实日志。分析日志不写密钥、图片 base64 或不必要的个人信息。证据文件用受控存储引用；原始输入、脱敏请求响应、输出图和评分通过同一个 run_id 关联。

## 5. 评测集怎么做

**已设计 20 条：12 条常规视觉任务 + 4 条视觉边界任务 + 4 条工程链路用例。** 这不是 20 条已跑完的数据。

18 小时建议先完成 P0 的 8 个视觉任务：C01–C04 用于发现问题和调试，C05–C08 留作验收；另做 C17–C20 工程演练，模拟结果单列。扩展 8 条有余力再跑。

你提供的素材文件夹已清点：70 张图片，主体集中在乳品单品和组合包装；还包含成品广告图、SKU 文字图等不应直接混入普通白底输入的素材。本轮从中选取了 16 张真实图片并记录路径、尺寸与 SHA-256。P0 的 8 张全部有素材：金盖鲜奶、绿色双瓶、双色奶壶、老酸奶单杯、柠檬包装、8 瓶组合、吸吸袋组合和双拼包装。验收选不同包装系列，但仍属于同一垂直品类，不能宣称已经覆盖全行业。

选中图片均为不带透明通道效果的白底图，适合核验抠图；图片观察和文件名给出的数量、规格只是初步核对，真实商品事实由你最终确认。图像是现成真实素材，不代表生成测试已经执行。附件素材清单包含取样理由；含广告标题、人物和复杂宣传排版的成品图不作普通 P0 输入。

每条输入要冻结：原图、真实商品事实、商品/任务名称、比例、背景和文案约束、要求产出张数。预期答案不是一张唯一标准图，而是可检查的约束和评分标准。

**A/B 对比协议：**

- A 是当前实现，B 是一次明确改进；保持同输入、模型、分辨率和候选数。本轮均先约定 2 张，不用 B 多生成几倍图片来放大采用机会。
- 先保存 A 的首轮结果再改动；重试单列，不能拿多次尝试里最好的一次代替首轮。
- C01–C04 可调参，C05–C08 在规则冻结后运行。若查看验收结果后继续调参，这四条已被污染，应更换新案例或说明只是调试结果。
- 评审时打乱图片，尽量不显示 A/B 版本。最好请老师/同学复核至少 2 个分歧案例；单人评审如实写。
- 当前只有 4 个验收任务，结论为探索性验证；不宣称统计显著、线上采用提升或广告 ROI。
- 是否消耗多少付费额度取决于实际调用组合，不能把 32 张合成图等同于 32 次付费生图。先设总预算、失败停止条件，再执行模型批量评测。

**评分标准 v0.1：**

| 类别 | 规则 |
| --- | --- |
| 商品事实硬门槛 | 外观、颜色、Logo、规格数量准确；不新增未经确认的材质/功效/价格 |
| 需求硬门槛 | 自定义内容、比例和约束得到执行 |
| 交付硬门槛 | 可读取、可导出，尺寸正确，无主体截断和关键文字缺失 |
| 层次构图 0/1/2 | 0 主次混乱或明显不合理；1 信息完整但较普通；2 焦点、留白和信息层级有意图 |
| 风格贴合 0/1/2 | 0 不符品类/任务；1 基本合适但通用；2 色彩材质氛围服务于这项商品需求 |
| 合成光影 0/1/2 | 0 破边、漂浮或光源冲突；1 大体自然有小瑕疵；2 边缘、接触阴影、透视和光源协调 |
| 文字可读 0/1/2 | 0 溢出、遮挡或难辨；1 可读但普通；2 对比和层级清楚、换行合理 |

采用规则为本项目试行标准：硬门槛全部通过，每个设计项至少 1 分，总分至少 6/8；再由你选“可直接采用 / 小改后采用 / 需重做”。小改暂定 10 分钟内的文字、颜色或局部位置调整，不包含重新抠图、重新找背景或重做版式。分数过线也不强迫采用；低于门槛却选择采用会提示复核。

另评整组差异：背景场景、构图、配色、信息层级至少两项有实质差异。只有同背景换左右位置通常不达标。用户明确要求极简留白时，应按构图与光影评价，不能把留白本身当错误。

工作簿使用顺序：评测集补素材 → 运行记录填执行与证据 → 图片评分逐张评 → 运行记录补组内差异 → 看评测汇总。浅黄格可填写，公式格自动更新。模板预留 A/B 各 20 个首轮记录、共 64 张视觉输出评分位；工程用例没有图片评分位。额外重试另存记录，扩容后再汇总，避免覆盖首轮。

## 6. Badcase 怎么复盘

你已经有一个最有价值的质量案例：**“能生成，但灰色空背景、文案版式固定，缺少设计感”。**

当前可以确定的代码事实：

1. 规划提示词要求连续背景和空桌面，并限制道具等视觉元素。
2. 回退背景为浅灰米白、留白、柔光。
3. 同一张背景用于两张成品，版式主要是 center/right。
4. 文字字体和颜色固定，策略中的 textColor 未被渲染消费。

因此有证据支持“系统策略和渲染限制是重要排查方向”。但要把某一次不好看的图归因到哪一条，还得拿到该次输入、规划结果、背景原图、最终合成图和版本。不能仅凭效果差就断言模型能力不足，也不能直接说回退一定触发。

按以下 8 项整理一页复盘：

1. 业务任务和预期：同商品，两个能用于讨论/继续采用的视觉方向。
2. 实际输出：保留两张原图，指出哪里重复、哪里不符合需求。
3. 影响：整组无可采用 / 差异不达标，分别影响哪个指标。
4. 证据：run_id、输入、约束、策略、模型、版本、原始输出和评分。
5. 归因：需求、输入、策略、生成、合成、存储、前端、评价标准中哪一步首先偏离。
6. 修复：只改有证据的环节，列出预期作用。
7. 回归：同输入比较，并覆盖极简等容易被误伤的场景。
8. 结论：已修复 / 仍失败 / 证据不足。无法验证时不写已关闭。

工作簿已经提供 3 条起始记录：用户反馈的同质化问题、静态确认的 textColor 映射缺口、已有 MOCK 保存失败演练。它们证据等级不同，当前都没有新回归结果。

**最省成本的修复顺序：** 先检查并修正策略参数到画布的映射，用固定输入做纯渲染验证；再改为两份明确设计 brief，生成两条方向；最后考虑换模型。每份 brief 至少含风格、场景、配色、商品位置、文字安全区、文案层级和禁止事项。提示词越长不一定越好，关键是策略可控且真的被下游执行。

## 8. 老师面前怎么展示

5 分钟顺序：

1. 40 秒：用户是谁、哪项设计任务、你当前聚焦什么。
2. 50 秒：北极星为何是采用任务，离线为什么先测首轮采用率；给出分子、分母与排除条件。
3. 70 秒：展示同一输入的两张样稿、评分依据与真实/模拟边界。
4. 80 秒：从 Badcase 沿 trace 找到偏离环节；哪些是确定事实，哪些是假设。
5. 60 秒：改了什么、同条件回归结果、样本局限与下一步。

常见追问：

- “为什么不看生成张数？”张数衡量产量，不能证明素材值得采用；多生成会增加费用，也可能只是重复。
- “审美主观怎么办？”拆成有锚点的设计维度，固定规则，保存判定理由，复核分歧，不把 LLM 分数当客观真值。
- “怎么证明是这个环节的问题？”看中间产物和版本，做固定输入的局部替换/消融，保持其他条件一致。
- “没有真实用户，北极星怎么用？”北极星先定义，当前报告离线案例结果，真实周采用数据尚未建立。
- “MOCK 有什么价值？”验证产品问题处理流程和证据结构；不能证明真实故障率、真实效果或真实改进收益。
